# Runtime & Platform Engineering for Production Agents

> Retrieval failures:** `openai.github.io/openai-agents-js/guides/human-in-the-loop/` returned only the nav shell on fetch (SPA); its API details below come from search-index snippets of that same page, flagged inline. Everything else resolved first try.


*Research brief, 2026-09-19. Target: an agent running entirely inside a Chrome MV3 extension — one service worker, multiple tabs, IndexedDB, no server, model provider as sole external dependency.*

## 1. Durable execution and resumability

**Practice.** Persist enough state that a crash resumes mid-run rather than restarting.

**Mechanism.** LangGraph compiles a graph with a *checkpointer* that writes a `StateSnapshot` at every **superstep**, keyed by `thread_id`; `interrupt()` inside a node persists state and returns control to the caller, and `Command(resume=...)` re-enters. Multiple `interrupt()` calls in one node are matched to resume values **by positional order** — a real footgun ([LangChain interrupts docs](https://docs.langchain.com/oss/python/langgraph/interrupts), accessed 2026-09-19). Temporal takes the opposite tack: **replay-based** durable execution, where the workflow is deterministic-but-not-predetermined and re-executes from an event history, with side effects quarantined in activities; Temporal states OpenAI's Codex web agent is built on it ([Temporal, "Of course you can build dynamic AI agents"](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal)).

**Evidence.** Diagrid's critique ([2025](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)) is the sharpest: checkpointing is *"I saved your state. You take it from here."* It leaves failure detection, recovery triggering, and dedup to you — *"if two processes try to resume the same `thread_id` simultaneously… LangGraph has no built-in coordination."* CrewAI persists only completed tasks/flows, not mid-ReAct iterations. The gap is always **mid-tool-call**: snapshot granularity is coarser than the side effect. The industry answer is idempotency keys derived from durable state — `(run_id, step_index, action_type)` — computed in the **tool wrapper**, not the prompt, with atomic claim → replay-stored-result → else execute ([TianPan, 2026-04-19](https://tianpan.co/blog/2026/04/19/idempotency-agentic-tool-calling-saga-deduplication); [2026-07-05](https://tianpan.co/blog/2026/07/05/the-idempotency-key-your-agent-forgot-to-send), which claims agents retry tool calls 15–30% of the time).

**MV3.** This is the section MV3 reshapes hardest. Chrome kills the service worker after **30s idle**, after **5 minutes on a single event-handler invocation**, and if a `fetch()` response takes **>30s**; Chrome 114+ keeps it alive for long-lived messaging, Chrome 116+ for WebSocket traffic; `chrome.alarms` minimum period is **30s** since Chrome 120 ([Chrome lifecycle docs](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)). **Replay-based durable execution is impossible** — you cannot guarantee a deterministic re-execution environment across a worker that dies mid-stream, and the 5-minute ceiling makes a long replay itself a termination risk. The honest substitute is **explicit event-sourced checkpointing at every step boundary**: append `{step_n, tool_name, args_hash, idempotency_key, status, result}` to IndexedDB *before* dispatching a tool and again on completion, then reconstruct the loop from the log on worker wake. Treat the service worker as a crash-prone executor, not a process. Long model calls must be **streamed** (streaming response chunks reset the fetch timer where the worker is otherwise active) and their partial output checkpointed, or the 30s fetch cap will kill you on a slow first token.

## 2. Orchestration topologies

**Practice.** Single loop, supervisor/worker, map-reduce fan-out, DAG, blackboard.

**Mechanism & evidence.** Anthropic's Research system is orchestrator-worker: an Opus 4 lead spawns **3–5 Sonnet 4 subagents in parallel**, each using 3+ tools in parallel. Reported numbers: **+90.2%** over single-agent Opus 4 on internal research evals, **~15× the tokens of chat** (agents alone are ~4×), **up to 90% reduction in research time**, and on BrowseComp three factors explained **95% of performance variance — token usage alone 80%** ([Anthropic, June 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). Their scaling rule: 1 agent / 3–10 calls for fact-finding, 2–4 subagents for comparisons, 10+ for complex research. Failure modes named: over-spawning on simple queries, duplicate work from vague task descriptions, endless searches for nonexistent facts.

The counterweight: Cognition's ["Don't Build Multi-Agents"](https://cognition.com/blog/dont-build-multi-agents) — parallel agents make *implicit* decisions that conflict at the action level (the Flappy Bird example). Their later ["Multi-Agents: What's Actually Working"](https://cognition.com/blog/multi-agents-working) converges on the same shape LangChain reports: **one main loop carries state, subagents are stateless read-only workers**. LangChain's framing is the usable rule — *reading is parallelizable, writing is not*; Anthropic deliberately synthesizes in **a single main agent in one unified call** because conflicting writes are far worse than conflicting reads ([LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)).

Framework state: AutoGen went to maintenance mode Oct 2025, superseded by Microsoft Agent Framework 1.0 (GA April 2026, merging AutoGen + Semantic Kernel, graph workflows with checkpointing, native MCP/A2A); CrewAI is fast to prototype but coarse on error handling and needs the most extra engineering to productionize ([n-ix comparison, 2026](https://www.n-ix.com/langgraph-vs-crewai-vs-autogen/)).

**MV3.** One service worker = one scheduler. **Fan-out is available and cheap in the right dimension**: tabs are your parallel workers. Adopt supervisor + *read-only* tab workers (open N tabs, extract, return structured findings), synthesize in the single main loop. **Do not** let two tab workers mutate the same page or the same task state. Note the MV3 tax: parallel tabs multiply memory in one browser process tree and every worker's result must round-trip through the service worker, which may die between dispatch and collection — so tab-worker results must land in IndexedDB directly from the content script, not be held in worker memory.

## 3. Tool interfaces as a standard

**Mechanism.** MCP standardises tool *description* and *invocation* over JSON-RPC: `tools/list` (paginated, cursor-based) returns descriptors of `name`, optional `title`, `description`, `inputSchema`, optional `outputSchema`, and untrusted-by-default `annotations`; `tools/call` returns `content` / `structuredContent` with `isError` for execution failures vs JSON-RPC errors for protocol failures. Servers declaring `tools.listChanged` emit `notifications/tools/list_changed`, which is the spec's hook for **dynamic tool exposure**. The spec says clients **SHOULD** keep a human in the loop able to deny invocations, show tool inputs before calling, and validate results before passing them to the LLM ([MCP spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)).

**Evidence on bloat.** MCP's own issue tracker estimates **~1,000 tokens per tool per session** ([modelcontextprotocol#2808](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/2808)). GitHub's official MCP server (**94 tools**) is reported at **17,600 tokens of definitions per request**; typical 20–30-tool sessions burn 15–30 KB before the first user message, and bloated tool sets are reported to drop selection accuracy from **43% to under 14%** ([mcp.directory, 2026](https://mcp.directory/blog/mcp-context-bloat-fix-2026-tool-search-code-mode-progressive-disclosure); [atcyrus](https://www.atcyrus.com/stories/mcp-tool-search-claude-code-context-pollution-guide)). Claude Code's Tool Search is reported at **85% token reduction, ~191,000 tokens of context preserved**.

**MV3.** Running an MCP *client* is feasible over HTTP/SSE; running local stdio servers is not — no subprocesses. The real lesson transfers without MCP at all: **your tool set is small and fixed, so gate it by phase**. Expose ~5–8 tools per phase (navigate/observe → extract → act) rather than 25 always-on. That's the measured guidance, implemented as a switch statement, not a protocol.

## 4. Streaming, interrupts, human-in-the-loop

**Mechanism.** AG-UI models the run as a typed event stream over SSE — run lifecycle, tool progress, state deltas, approval requests, cancellation — so the frontend renders a workflow rather than a typing indicator ([Microsoft Learn, AG-UI integration](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/ui/ag-ui/)). OpenAI's Agents SDK marks tools `needsApproval`, evaluated **per action before execution** so one approval can cover a `move + click` sequence; the run pauses, `stream.completed` resolves, and `stream.interruptions` carries pending approvals to `approve()`/`reject()`, with `RunState` serializable for cross-process resume (from search-index snippets of the [Agents SDK HITL guide](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/) — **page itself fetched as SPA shell only**).

**MV3.** Extensions have a better primitive than SSE: `chrome.runtime` ports. But **a closed popup destroys the UI mid-run**, and since Chrome 114 opening a port no longer resets the idle timer (messages do). So: the event log in IndexedDB is the source of truth and the UI is a *replayer*, not a listener — panel opens, reads log tail, subscribes to deltas. Coalesce high-frequency events (batch per animation frame) or the message channel becomes the bottleneck. Approvals map cleanly: persist `{status: "awaiting_approval", proposed_action}`, let the worker die, resume on user click. A pause-for-human costing nothing is the one place MV3 is *better* than a server runtime.

## 5. Isolation and sandboxing

**Mechanism.** Server-side browser agents give each run an ephemeral microVM or container with its own filesystem, network stack and cookie jar, destroyed at exit; the stated test is whether you can point to the line of code guaranteeing session B never sees session A's cookies ([Novita](https://blogs.novita.ai/browser-computer-use-sandbox-isolation/), [Browserbase](https://www.browserbase.com/blog/internal-agents)). Sandboxing the process does **not** sandbox the secret: Anthropic's sandbox-runtime substitutes a **per-session sentinel** for the real credential and swaps it back only at egress behind a TLS-terminating proxy ([Zujkowski, 2026-07-02](https://williamzujkowski.github.io/posts/2026-07-02-agentic-ai-sandbox-secret-proxying-gap/)).

**MV3 — this inverts completely.** The agent runs *in the user's own session*: their cookies, their logged-in banking tab, their SSO. There is no per-run isolation and **no credential vault is needed or possible** — the browser already holds the credentials and the agent can never see them, which is strictly better than a server agent holding plaintext secrets. What you lose is containment: a prompt injection on page A acts with full ambient authority on page B. Honest substitutes: (a) an **origin allowlist per run**, declared before the run starts and enforced in the tool wrapper; (b) treat all page text as untrusted data, never instruction; (c) **mandatory approval for irreversible actions** (payment, send, delete, OAuth grant) — the approval gate *is* your sandbox boundary; (d) optionally run in a dedicated profile/container tab to approximate session isolation, at the cost of losing the logged-in session that made the extension worth building.

## 6. Observability and cost control

**Mechanism.** OTel GenAI semconv defines `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.agent.name`, and `gen_ai.usage.input_tokens` / `output_tokens` (plus `reasoning_tokens`), with opt-in capture of prompts, completions and tool results ([OTel GenAI attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/); [agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). Status as of **March 2026: mostly experimental** — chat/embedding attributes are stable enough for dashboards, agent and tool-orchestration conventions still settling ([OTel blog, 2026](https://opentelemetry.io/blog/2026/genai-observability/)).

**Evidence.** The consistent operator claim is that budget control must sit **in the execution path, evaluated before each LLM call**, not in a retrospective dashboard ([Oracle, runtime budget guardrails](https://blogs.oracle.com/ai-and-datascience/runtime-budget-guardrails-agentic-ai); [waxell, 2026](https://waxell.ai/blog/ai-agent-token-budget-enforcement)). The trio teams name as non-negotiable: per-request token spend, tool-call traces, and the point where a run went sideways. The best traces come from the runtime that already knows what the agent is doing, not a wrapper bolted on afterwards ([Braintrust, 2026](https://www.braintrust.dev/articles/agent-observability-complete-guide-2026)).

**MV3.** No collector, no backend — but you already have the event log from §1, so **name its fields with OTel GenAI attribute names** and you get portability for free. Budget enforcement is trivial and belongs in the same wrapper as the idempotency key: refuse the call if cumulative `input_tokens + output_tokens` exceeds the run cap. Graceful degradation: drop to a cheaper model, shrink the observation (accessibility tree over full DOM), then stop and ask the user. Storage caveat: `chrome.storage.local` is capped at **10 MB** (5 MB pre-Chrome 113) unless you request `unlimitedStorage`, and **IndexedDB sits under the global quota manager and is evictable under disk pressure even with that permission** ([Chrome storage docs](https://developer.chrome.com/docs/extensions/reference/api/storage); [chromium-extensions thread](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/EfAXciu90yY)) — so cap trace retention and treat the log as durable-enough, not durable.

## Adopt five

1. **Step-boundary event log in IndexedDB as the single source of truth.** Everything else — resume, UI replay, cost accounting, approvals — falls out of one append-only table. Forced by the 30s/5min worker lifecycle, not optional.
2. **Idempotency keys in the tool wrapper**, derived from `(run_id, step_index, action_type)`. The worker *will* die between "clicked Submit" and "recorded that I clicked Submit"; without this, resume double-submits.
3. **Approval gates on irreversible actions, modelled as persisted state.** MV3 has no sandbox, so the gate is the security boundary — and a pause costs nothing when the worker is designed to die anyway.
4. **Phase-scoped tool exposure (~5–8 tools).** 43%→14% selection-accuracy collapse under bloat is the cheapest quality win available, and it's a switch statement.
5. **OTel-named per-step token/cost accounting with a hard pre-call budget check.** Enforced before the call, degrading model→observation-size→ask-user.

## Skip three

1. **Replay-based durable execution (Temporal-style).** Requires deterministic re-execution the service worker cannot provide, and replay itself can exceed the 5-minute cap. Checkpoint-and-resume is the correct weaker guarantee.
2. **Writing subagents / true multi-agent.** Anthropic's +90.2% came with ~15× tokens on a *research* workload where reads parallelize; browser automation is write-heavy and Cognition/LangChain both report conflicting writes are far worse than conflicting reads. Read-only tab workers, single synthesizing loop — stop there.
3. **An MCP client and credential vault.** No stdio servers without subprocesses, the tool set is small and fixed, and the browser already holds the credentials more safely than you could. Both are answers to problems a server-side agent has and this one does not.

## 250-word summary

The six practices split cleanly into what MV3 forces on you and what it forbids.

**Forced:** durable state. Chrome terminates the service worker after 30s idle, 5 minutes on one handler, or a 30s-slow `fetch`, so the agent must be event-sourced — append `{step, tool, args_hash, idempotency_key, result}` to IndexedDB before and after every tool dispatch, and rebuild the loop on wake. Temporal-style replay durability is impossible here (no deterministic re-execution, and replay itself risks the 5-minute cap); LangGraph-style checkpoint-and-resume is the honest substitute, with its known gap — Diagrid's point that checkpointers leave failure detection and dedup to you — closed by idempotency keys computed in the tool wrapper, never the prompt.

**Forbidden:** isolation and multi-agent. There is no per-run sandbox; the agent runs in the user's live session with ambient authority. No credential vault is needed (the browser holds them) but nothing contains an injected page either, so approval gates on irreversible actions *are* the security boundary. On topology, Anthropic's +90.2% research result came at ~15× tokens on a read-heavy workload; browser automation is write-heavy, and Cognition and LangChain agree conflicting writes are far worse than conflicting reads — so read-only tab workers plus one synthesizing loop, no writing subagents.

**Cheap wins:** phase-scoped tool exposure (bloat drops selection accuracy 43%→14%), OTel-named token accounting, and pre-call budget checks. Skip MCP entirely — no stdio subprocesses, fixed small tool set.
