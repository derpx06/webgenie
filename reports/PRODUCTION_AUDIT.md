# Production audit — what stands between WebGenie and users who are not watching

Read-only audit of the working tree at `aa7f3cf`, version `0.1.13`. Every row was checked
against the source, not against `docs/`. Where `reports/PLAN.md` already schedules a fix, the row
says so — a planned fix is still a shipping blocker until it lands.

**The shape of it.** The guard *architecture* is unusually good for this class of product: the
commit question is written by the system and not by the model, the intent check is genuinely
page-blind, secrets are placeholders bound to a host, route memory stores no typed text, the trace
store evicts and redacts. What is not ready is the *defaults and the edges*: three of the guards
are voided by markup the attacker page controls, the firewall is on and enforces nothing, telemetry
is on and contradicts `DECISIONS.md` D1, the product is dead on arrival until the user finds a
control nothing points them at, and on a default install a failed task leaves no evidence at all.

Severity: **blocker** = a non-watching user can lose money, data or account control, or cannot use
the product, or the extension would be rejected at review. **serious** = real harm to trust,
diagnosis or usability. **polish** = worth doing, harms no one.

## 1. Durability — MV3 worker death

Keep-alive is an offscreen document holding a port and pinging every 20 s
(`chrome-extension/src/background/services/keepAliveManager.ts:19-39`,
`chrome-extension/public/keep-alive/keep-alive.js:5-35`), started in `runExecutor`
(`index.ts:168`) and stopped in its `finally` (`index.ts:175`). While that holds, the 30 s idle and
5 min limits do not apply. The question is what happens when it does not hold — an extension
update, a crash, an OOM eviction.

### What is actually saved

`Executor.saveCheckpoint` (`agent/executor.ts:854-886`) writes exactly fifteen fields:
`taskId, task, status, step, currentContract, lastObservationId, validatedProgress, blockedState,
updatedAt, tabId, tasks, pendingQuestion, approvedCommitKey, declinedCommitKeys, interruption`.
The transcript lives separately in `chrome.storage.session`
(`agent/messages/service.ts:100-106`), written after each completed batch.

`AgentContext` (`agent/types.ts:100-175`) holds roughly thirty more fields that are **never
persisted**: `findings`, `ledger`, `requirements`, `consecutiveFailures`, `stalls`,
`actionRepeats`, `refusedActions`, `openedAddresses`, `typedValues`, `usedEntries`, `emptyScrolls`,
`stagnantActions`, `echoRejections`, `requirementRefusals`, `visitedUrls`, `intentDecisions`,
`intentRefusals`, `secrets`, `entryCandidates`, `lastDragKey`, `taskStartUrl`, `routeSteps`,
`downloads`, `files`.

**Answer to the posed question.** Yes: a click can be submitted, the worker can die before the tool
turn or the checkpoint records it, and the resumed task can issue it again — with the commit
approval still marked unspent. There is no idempotency key anywhere. What is lost on a crash is the
last step's actions, every fail-open guard counter, the findings, the requirements list and the
in-memory secrets.

### Plainly: can an injection on a visited page…

- **Cause a commit or purchase?** **Yes.** Three independent bypasses, each one attribute of
  markup: an `<a href>` or `aria-expanded` on the control (2.1), a non-English or icon-only label
  with no card fields in the form (2.7), or `fill_form {submit:true}` with focus outside the form
  (2.2). What still works: a plain `<button type="submit">Place order</button>` in a form with card
  fields is caught, the question is system-written so the page cannot word it, and an unanswered
  question pauses the task rather than auto-approving. The failure mode is a **silent** purchase,
  not a coerced yes.
- **Navigate to an attacker URL?** **Yes, by design.** One `<a href>` on the page satisfies
  `urlHasProvenance` (`navigator.ts:394-398`) and the intent check is never reached. The firewall
  would be the backstop; it is empty (2.3).
- **Cause a secret to be typed?** **Not an existing one** — `sameSite` binding at
  `navigator.ts:763` holds, and the plaintext never enters any model context. **Yes for a fresh
  one**, via a model-authored `ask_human` password prompt bound to the attacker's host (2.6) — but
  that needs the user present, which is outside this audit's scenario.
- **Exfiltrate data?** **Yes, with all default settings**, via 2.4. Everything the agent read —
  inbox contents, order history, `save_findings` output, working memory — can ride out in a query
  string. Secondary channels (`read_file`, `fetch_json`, `eval_js`) need `enableAdvancedTools`.

## 4. Failure surfaces the user sees

The render path is the same for everything: `emitEvent` → `EventManager.emit` →
