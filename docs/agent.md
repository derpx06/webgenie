# How the agent works

A description of the shipped agent, checked against the source. Paths are under `chrome-extension/src/background/` unless they start with `packages/`, `pages/` or `chrome-extension/`.

## Runtime

- The background service worker (`index.ts`) accepts one long-lived port, `side-panel-connection`, from `side-panel/index.html`. Everything the UI can do is a message on that port (see [Commands](#commands)); agent progress comes back as `EventManager` events on the same port.
- `agent/executor.ts` runs one task with two model roles: `PlannerAgent` (`agent/agents/planner.ts`) and `NavigatorAgent` (`agent/agents/navigator.ts`). There is no validator agent.
- Browser control is puppeteer-core over `chrome.debugger` (`browser/page.ts`, `browser/context.ts`); the firewall (`isUrlAllowed`) is enforced on every navigation.
- The content script (`pages/content`) only draws the ambient border and status capsule; `core/tab-orchestrator` groups task tabs and maps agent events to a workflow stage for that UI.

## Commands

The switch in `index.ts` handles: `heartbeat`, `new_task`, `follow_up_task`, `cancel_task`, `pause_task` / `resume_task` (in-memory pause), `human_response`, `reattach`, `resume_saved_task`, `discard_saved_task`, `screenshot`, `state`, `nohighlight`, `speech_to_text`, `replay`, and `parallel_task` / `resume_parallel_task` ([Orchestration](#orchestration)).

## Task lifecycle

- **Checkpoints** (`agent/contracts/checkpoint.ts`) are saved to IndexedDB (`agent:checkpoint:<taskId>`) at task start, after each planner run and each navigator step, and on interruption. They hold the task list, step, current contract, validated progress, blocked state, tab, pending question, approved/declined commits and the interruption reason. The transcript is in `chrome.storage.session`, and `webgenie_active_task` points at the running task. `completed` / `failed` (including `cancel_task`) delete the checkpoint; `running`, `waiting_human` and `paused` are resumable. A restored task whose page changed starts with a re-observe result, which forces a replan.
- **Interruption**: the side panel disconnecting, the agent's tab closing, the debugger being detached by the user, the answer deadline passing, or rate limits or a lost connection to the model provider outlasting their retry budget call `executor.interrupt(reason)`. The task ends with `task.pause` and a saved `paused` / `waiting_human` checkpoint instead of failing.
- **Answer deadline**: a question to the user waits `humanWaitMinutes` (default 10). When it expires the task is interrupted and saved ("Still waiting for your answer…").
- **Reattach**: the side panel sends `reattach` when it reconnects. A live task re-emits its pending question; a checkpoint left `running` (the worker died mid-task) resumes by itself; any other resumable checkpoint is offered to the user as `task_resumable`, answered with `resume_saved_task` or `discard_saved_task`.
- **Late answers**: a `human_response` with no live task waits for an ending task to finish, loads its checkpoint and resumes with the answer applied.

## The step loop

Per step `executor.ts`:

1. checks stop, pause and the answer wait (`shouldStop`), and `maxFailures`;
2. asks `contracts/replan.ts` whether to plan. Triggers in order: `initial`, `human_needed`, `completion_refused` (the last plan was sent back, see below), `contract_complete` (navigator said done), `navigator_error`, `validation` (two unvalidated steps in a row), `progress_stall` (same actions on the same layout 3 times in the last 6 steps), `step_interval` (`planningInterval`, default 5). The interval re-plan waits while every navigator step since the last plan validated `passed` and that plan moved no requirement from `applied` back to `pending`; it still fires at twice the interval;
3. builds the page state once and shares it between planner and navigator;
4. runs the planner when planning, then the navigator (up to `maxActionsPerStep` tool calls), saving a checkpoint after each. The navigator never runs without a plan: a first planner call that failed (a timeout, an error, which counts toward `maxFailures`) is made again on the next step.

Failure budget: a step whose last validated action passed (or a done) resets `consecutiveFailures`; a failed action adds 1, or 0.5 when it threw a page-side error (`isPageSideError`: a covered target, no visible area, a site connection error such as `net::ERR_CONNECTION_RESET`); a stale-element error adds nothing; a stall adds 1. The task ends at `maxFailures` (default 3).

**Completion is the planner's call.** The navigator's `done` only triggers a planner check. Every plan carries `requirements`, the task's constraints (a range, the order a superlative implies, a count, an attribute), each marked `applied` (with evidence quoting the page text or naming a URL parameter), `not_available` (with the reason) or `pending`; the list is shown to both models as `[REQUIREMENTS]`. A new plan's list is merged into the one held, not substituted for it: a requirement whose application validated stays `applied` however the planner rewords it, and only evidence gone from the current page reopens it, once (a live run re-applied one filter three times because each plan reset it to `pending`). Verifying an applied requirement happens on the current state: a `go_back` off a page that still shows its evidence is refused once, naming what would be lost, and a page that could not be read is never taken as proof the evidence is gone. A planner `done` is sent back, in this order:

- the answer echoes action results ("Clicked …"): at most twice (`echoRejections`);
- a requirement is `pending`: at most twice (`requirementRefusals`); a later done is accepted and the answer gets "Not applied: …" appended;
- an `applied` requirement's evidence (its double-quoted texts and `name=value` parameters) is in none of the current page's text, element attributes or address, decoded or not (`staleRequirements`): once per task; evidence with nothing to search for is not judged;
- an answer of absence ("no results", "not found", "could not find", …) or a navigator done with `success: false`, on an http(s) page that was not read (`read_page`, `find_in_page`, `extract`) at the current address and shows no empty-result message (`absenceUnread`): once per task;
- the answer does not carry what the task asked for (`answerGaps`): it says what was asked for is on the page without naming any of it (its words and numbers are all the task's own, "cars are displayed for sale near Kentwood, MI", "the search returned 67,163 results"), the task asks for a value (a price, a count, a date, a rating) and the answer states no number the task did not already give, or the task asks for several things (`askedParts` splits it on an "and" that a question word or an asking verb follows, never on one inside a description) and the answer says nothing about one of them; once per task. For the first two, an answer saying plainly that the page does not give it is never sent back; the third is sent back even then, so the answer covers every part.

A plan that is not done is checked for a repeated goal (`GoalRepeats` in `contracts/replan.ts`): goals whose words (lowercased, punctuation, short words and stopwords removed) overlap by at least 75% count as the same. The third plan of one goal without progress is sent back with the goals already tried; from the fifth the planner is told to finish with done and the best answer it has, that done is accepted without the checks above, and a plan that still is not done ends the task (`MaxFailuresReachedError`). Progress clears the counts: a `passed` navigator step whose actions and layout this task had not recorded before, a new finding, a requirement newly marked `applied`, or an answer from the user.

A sent-back plan replans at once (`completion_refused`) with the reason as its action result, without a navigator step. When the task finishes, the executor looks for the answer's values (numbers and quoted text, at least 3 characters) in the last page read of the current address; if some are there and none is in viewport text, it scrolls the longest of up to three into view (`scrollToText`, no model call). `validation/done-evidence.ts` computes whether a `done` is backed by evidence (navigator success, final phase of the plan, no pending question or declined commit, every action in the phase validated, page text read, numbers and quoted values in the answer present on the page) and logs it next to the planner's verdict (`verify.skippable`). Only with `acceptEvidencedDone` on (default off, no UI) does an evidenced `done` skip the planner (`verify.skipped`).

`contracts/execution-router.ts` handles one deterministic case: a task that is only "go to / open / visit <url>" runs `go_to_url` without a planner call; the planner still confirms completion.

There is no input token budget: context is bounded by character budgets in `agent/memory/in-chat/context-builder.ts`, and output by `maxTokens` in `agent/helper.ts`.

## What the models see

`MessageManager` (`agent/messages/service.ts`) keeps the transcript: `task` and `human_answer` messages plus one tool call/result turn per executed navigator action. `ContextBuilder.buildContextPacket` sends the static system prompt, the tasks and answers, then one final state message with: the start page, earlier completed tasks, the current plan, the requirements checklist, findings, blocked state, and the page state (with the control summary above the element list).

- The planner also gets validated progress (last 12 records) and every step as text; its packet contains no tool calls.
- The navigator gets its recent tool turns as real messages (at least 3, from a boundary that moves in blocks of 8) and older steps as a short text summary.
- Page and tool text is wrapped as untrusted content (see [Safety](#safety)).

## Perception

`browser/chromium-apis/ax-tree-extractor.ts` reads `Accessibility.getFullAXTree` for every frame session plus one `DOMSnapshot` per session (boxes, tag names, input types), and `browser/dom/ax-tree-pruner.ts` turns it into the indexed element tree (`browser/dom/views.ts`). No script is injected for perception. Elements are located by `backendNodeId` in the frame they were read from; clicks and typing are CDP `Input` events. Interaction highlights are drawn separately (`browser/dom/service.ts`); every `chrome.scripting` injection runs `injectImmediately` and gives up after 10 s (`SCRIPT_TIMEOUT_MS`, `adapters/ChromeBrowserAdapter.ts`).

- **Control summary.** Above the element list, `controlSummary` (`agent/prompts/base.ts`) writes `Collapsed sections:` (non-field elements with `aria-expanded="false"` or an unexpanded `aria-haspopup`, up to 15 by index and name, then a count) and `Controls:` (checkboxes and switches with how many are checked, radio buttons with how many are selected, selects, sliders).
- **Custom checkboxes and radios.** An `<input type=checkbox|radio>` with no box (hidden and drawn by its label) puts `checked="true|false"` on its label, found by `for` or as an ancestor (`labelHiddenChoices` in `ax-tree-extractor.ts`). Pointer actions on an element without a box aim at its visible label, else its first descendant with a box (`pointerTarget` in `browser/page.ts`).
- **Native selects** are one element: the options are not listed as elements; `value` is the selected option and `options` holds the option names joined by ` | ` when there are at most 10, else their count. `select_dropdown_option` matches the option text exactly, then ignoring spacing and case.
- **Skip links** ("Skip to …", "Skip navigation" linking to a fragment of the same page) are dropped.
- **Sparse reads.** A read with at most 2 interactive elements (`SPARSE_READ_ELEMENTS`) right after a navigation, or while the document is still loading (waited on once per URL), is re-read every 400 ms for at most 3 s: it stops when more controls appear, when the read fails, or when the document has loaded and a re-read found no more elements (two re-reads for a page with none).
- **New tabs.** A click or right click that makes the page open a window (`Page.windowOpen`) waits up to 2 s for the tab to be created. Tabs that have not committed a page are listed with their `pendingUrl` (or `about:blank` while loading), and `switchTab` waits for the tab to load before reading it; the pointer action switches to a tab it opened.
- **Covered targets.** A pointer action on a disabled element, or one whose centre is covered, is not sent. The error names the cover (`coverBlocker`): the target's own or the focused field's open list or menu ("choose an option from it, or press Escape"), else the covering layer (the nearest dialog or fixed/sticky ancestor, or the open dialog a textless backdrop belongs to) by `aria-label`, `aria-labelledby`, heading or text, with those of its (up to six) buttons found in the last read, by index.
- **Date and time inputs.** Native `date`, `time`, `datetime-local` and `month` inputs get their value set directly from text written as a person would (ISO, `05/20/2024`, `20/05/2024` when the first part is over 12, `May 20, 2024`, `3:30 PM`, …; `toNativeInputValue`); text that does not parse is an error naming the expected format. `week`, `color` and `range` inputs are set directly with the text as given.

Defined in `agent/actions/schemas.ts`, registered in `ActionBuilder.buildDefaultActions()` (`agent/actions/builder.ts`). Every tool also carries a required `memory` string.

Text matches as whole words, case and spacing aside (`findWholeText`); a condition already true when the wait began says so instead of reporting a wait, and a `text_gone` that times out quotes the passage still holding it |
| `read_page` | `target?` (`current` or a URL to open), `mode?` (`main` the article or result list without navigation, `full` every text, `structured` the heading outline only), `max_tokens?` (200-8000, default 3000), `section?` (an outline id `s3` or a heading text), `cursor?` (character offset to read on from), `all_pages?`, `max_pages?` (1-20, default 5). The page is extracted **in the page** (`browser/dom/read-page.ts`, run through `page.readPageMarkdown`) and returned as markdown: headings, paragraphs, lists, compact markdown tables, links as `[text](url)`. `main` drops landmark navigation/header/footer/aside, `role=` navigation, banner, contentinfo, complementary, search, dialog, menu and toolbar, elements that are hidden or `aria-hidden`, fixed and sticky containers (cookie bars, sticky headers, chat widgets), and blocks of five or more short links that are almost all link text; the content element itself is `<main>`/`[role=main]`/`<article>`, else Readability's paragraph-parent scoring. A page longer than the budget returns its first part, the outline (`s1 ## Title [1204 chars]` per heading) and a cursor; `section` jumps straight to one. `all_pages` follows `rel=next` or a link labelled exactly next/older/»/›/→, else scrolls to the bottom of a list that grows, and reports how many pages it read. An extraction that fails or comes back empty falls back to the raw page text |
| `find_in_page` | `query`, `regex?`, `max_snippets?` (1-30, default 8). Searches the full extraction (navigation included) without a whole-page read; each match comes back with the text around it — a match inside a table row returns that row with its header — and the index of the listed element whose own text or labels carry it |

The result carries the JSON, `per field: name=table(0.90), rating=model(0.50)`, and anything that does not match the schema. A field nothing resolved is reported as not found |

| `view_screenshot` | none; the next state carries a screenshot of the viewport with element indexes drawn on it. Images go only in the last message, never into the transcript |

What `NavigatorAgent` adds to action results, and what it refuses (`agent/agents/navigator.ts`):

- **Batches** stop after an action (not the last) that revealed options or menu items, elements inside a dialog, or form fields unlike any in the earlier read (`revealedControls` in `validation/observation.ts`); other new elements do not stop the batch. The result names the revealed options ("A menu or list opened: …") and dialog elements, up to 5 each by index and label.
- **Typing.** `input_text` into a field that offers suggestions (`role=combobox`, `aria-autocomplete` list/both/inline, `aria-haspopup=listbox`) without `submit` waits 500 ms wherever it is in the batch and lists the suggestions (new options, else the option and menu items in the viewport) or says none appeared. New text that reads as the field's complaint ("required", "invalid", "select … from", …) and `aria-invalid="true"` on the field are reported.
- **Navigation results** from `go_to_url` say where a redirect landed when the final address differs (`redirectNote`; addresses compared by `addressKey`: scheme, `www.`, trailing slash and fragment aside, query kept).
- **Opening one address again.** After 3 opens without error of the same `addressKey` with `go_to_url` (`MAX_OPENS_PER_ADDRESS`), the next one is refused.
- **Scrolls.** A page scroll (no `index`) reports how many new elements it revealed. When the element list is windowed around the viewport (longer than `MAX_INTERACTIVE_ELEMENTS_CHARS`, `elementsWindowed`) it says it moved the listed part instead, and it never counts as empty. After 3 page scrolls in a row revealing nothing (`MAX_EMPTY_SCROLLS`; any other action, and any scroll that revealed elements, added text or made the page longer, resets the count) the next page scroll is refused. From the 4th scroll in a row each result carries a note to use offscreen elements by index, open collapsed sections or search the text, naming the empty-scroll count from 3.
- **Repeated actions.** The same action (name, page `addressKey`, arguments without `memory`) executed a 3rd time gets a note to do something different, and the 4th is refused (`MAX_IDENTICAL_ACTIONS`). Any action that changed the page (new elements, new text, another address, a longer page) clears every count, so pagination, "load more" and a list that loads while it is scrolled keep working. `scroll` (which has the empty-scroll count), `done` and `ask_human` are not counted.
- **Verification challenges.** An indexed action (other than `scroll`) on an element that is part of a CAPTCHA or bot check (`isChallengeElement`: its or an ancestor's name, or a frame from a challenge provider) is refused with an instruction to ask the user once, or, after the user was already asked about one, to finish with done (success: false). A mutating action after which the page text shows challenge wording it did not show before (`challengeOnPage`) gets the same instruction.
- **Questions.** `ask_human` is refused when it only offers to retry or try another approach (`offersToRetry`: "Should I try again?", "Would you like me to search the web instead?"), unless it is a confirmation, has fields, or mentions money, an account or personal data (card, payment, account, password, address, order, subscription, delete, cancel, refund, booking, …); when its normalized text equals a question the user already answered in the conversation (the refusal quotes the answer); and when it is about a verification challenge after one was already answered.

`manage_bookmarks`, `manage_reading_list`, `manage_history`, `manage_downloads`, `manage_tabs`, `manage_windows`, `manage_privacy`, `manage_extensions`, `manage_system` and `manage_sessions` are registered only when **Options → Advanced → browser data tools** (`enableBrowserDataTools`, default off) is on.

## Verification

`agent/validation/`:

- `service.ts` — `validateActionOutcome` compares observations before and after each mutating action and sets `ActionResult.validated`; also the commit gate, personal-data detection, same-site checks, stale-index handling, `addressKey`, and the verification-challenge and question helpers. A `click_element` whose address changed only in its fragment, or whose document changed while the address (fragment aside, active tab included) and the visible content (`visibleContentKey`: title, elements' role, tag, label and state, page text) stayed the same, is `unknown` with `retry_reobserve` and a result saying the page did not change, not `passed`.
- `observation.ts` — `BrowserObservation`, visible and viewport text, appeared text, new elements and `revealedControls` (options, dialog elements, new fields), target fingerprints.
- `settling.ts` — `waitForActionSettled` polls until the page holds still, and then once more to see it quiet, which typing and a page scroll that moved the window without making the page longer skip (their own result is the evidence).
- `done-evidence.ts` — the evidence check, `absenceUnread` and `staleRequirements` described above.

## Safety

- **System-built commit confirmations.** `click_element` and `send_keys` require `commits` (`none | order | payment | subscription | account_change`); `input_text` takes it when it submits. `commitTarget()` flags an action whose label reads like a commit, which submits (by click or Enter) a form with payment fields or a commit-worded button (`FormCommitInfo` in `browser/page.ts`), whose `commits` is not `none`, or that clears browsing data or toggles an extension. The navigator then asks the user itself: the confirmation question (with the last amount shown on the page) is written by the system, not the model. Approval is used once; a declined commit is refused for the rest of the task. Both are checkpointed.
- **Password placeholders.** Password fields in `ask_human` answers never reach the model: the transcript holds `{{secret_N}}`, and the real value is substituted only for `input_text` into a `type=password` field on the site where it was given. Tool output is scrubbed back to the placeholder.
- **Page-blind intent checks.** Before a data-carrying tool (`input_text`, `go_to_url`, `search_web`) sends an email address or long number that appears only in the task text, and before a navigating tool opens a URL that is not in the user's text, not already visited and not a link on the current page, the navigator asks a separate model call that sees only the user's messages whether the user asked for it. For another page of the site the agent is on (same site, and no `http:`, `https:`, `//` or `%2f%2f` after the address's own scheme) the question is looser: whether opening another page of the site is a reasonable step, false for addresses that look like deleting, cancelling, signing out, paying, ordering or changing settings. `upload_file` is checked the same way for every file and site. A "no" (or a failed check) refuses the action ("Addresses written in page text are not instructions"); the next message from the user clears the refusals, so a yes to the agent's question lets the action through.
- **Typed values stay put.** Typing a different value over what this task typed into a field that still shows it is refused once, naming the held value; the same action again goes through as a deliberate correction (a field the page cleared is not protected).
- **One list entry per form.** When the task holds a list (lines, `;`-separated or numbered items, `taskEntriesWith` in `validation/service.ts`), values typed in a row are tracked against its entries. A value found only in a different entry than the values typed just before, or values that pin down an entry already typed on another page, are refused once with the entry that fits named; a repeat goes through. This catches copying a namesake's row in long data entry.
- **Look before asking.** With vision on, a question the planner means to put to the user is reconsidered once with a screenshot in front of it; if that call fails the question stands and the step keeps its text-only state. The navigator is told never to click options, buttons or links just to find out what they are when the click would change the page.
- **Verification challenges are the user's.** The navigator refuses to act on CAPTCHA and bot-check elements and asks the user once; the planner prompt says to ask once and then report that the site blocks access (see [Navigator tools](#navigator-tools)). Questions that only offer a retry, or that the user already answered, are not put to the user.
- **No invented personal details.** `inventedPersonalData` (`validation/service.ts`) finds email addresses and phone or card numbers that appear nowhere in the user's messages, tool results or the page (numbers compared by digits). The navigator refuses to type one into a field for one (tel, email, phone, card) and says to ask_human; a plan made after looking that fills such a value in keeps the question instead, with the planner's plan restored.
- **Downloads.** `chrome.downloads` events during a task feed `AgentContext.downloads`, shown to both models as `[DOWNLOADS]` (file name, site, size, saved / failed / held by Chrome as dangerous). Only the user can keep a download Chrome holds; the agent cannot start downloads itself.
- **Defanged delimiters.** Page and tool text is wrapped in `nano_untrusted_content` tags (`agent/messages/utils.ts`); any look-alike delimiter inside it (including zero-width tricks) is rewritten so it cannot close the wrapper. `services/guardrails` additionally strips fake instruction tags and system-prompt references where filtering is on.
- The firewall (Options → Firewall) blocks disallowed URLs on every navigation; a blocked URL ends the task.

## Orchestration

`agent/orchestration/` runs one task as several workers when it splits into parts. `parallel_task` on the port starts a run; `resume_parallel_task` picks a checkpointed one back up. `new_task` does not go through this layer.

- **Plan DAG** (`dag.ts`, `decompose.ts`). One model call (the planner's model, before any page is opened) splits the task into parts with explicit dependencies, each `parallel-safe` or `serial`, each with its own step and token budget and its own success criteria. Anything unusable — bad JSON, a cycle, an unknown dependency, more than eight parts — falls back to the single-node plan, which is the ordinary path: one worker, the user's task text unchanged, no blackboard context, no verification call.
- **Workers** (`pool.ts`, `worker.ts`). Each part is an ordinary `Executor` with its own `BrowserContext`, its own tab and the task id `<runId>:<nodeId>`, which namespaces its transcript, its step checkpoint and its trace records. Concurrency is what the caller asks for, lowered by `navigator.deviceMemory` and `hardwareConcurrency`, capped at 8.
- **Brief** (`brief.ts`). A worker is told its own part, its success criterion, what the parts it depends on answered, and which addresses other workers have already read — not the whole task, because the completion checks in `validation/done-evidence.ts` read the task text as what the answer must cover.
- **Blackboard** (`blackboard.ts`). An append-only IndexedDB record of facts, addresses, artifacts and failures (`orchestration:blackboard:<runId>`). `claim()` gives an address to exactly one worker, so two workers never read the same page; the block a worker sees is rendered by `TaskLedger`.
- **Supervisor** (`supervisor.ts`). A worker with no progress for `stuckMs`, the same progress signature `loopThreshold` times, or more than its node's token budget is killed. The node is retried with exponential backoff, escalated to the stronger model, then given up on; every decision is recorded on the node and in the checkpoint.
- **Cost governor** (`governor.ts`). One budget of *uncached* input tokens across all workers. As it runs down: screenshots go, then concurrency drops to one, then both roles move to the cheaper of the two configured models. Only an exhausted budget stops dispatch; what is running finishes.
- **Verifier** (`verifier.ts`). After the plan has run, a separate call re-checks every part's claim against the blackboard's evidence alone — never the call that produced the answer. A claim that does not hold re-dispatches its worker (two rounds at most). A claim from a failed part is refused without a call; a verification call that fails leaves the report `inconclusive` and re-dispatches nothing.
- **Checkpoints** (`checkpoint.ts`, `orchestrator.ts`). The run is written to `orchestration:run:<runId>` after every node, beside each worker's own `agent:checkpoint:<runId>:<nodeId>`. `resume(runId)` restores the plan, the blackboard and every finished part; a node that was running when the service worker died is pending again and runs from scratch, so at most one node's steps are lost.

**What MV3 does not allow, honestly.** Everything is one background service worker. There is no second process, no second browser context and no incognito split, so workers share cookies, site storage, the network and this extension's state: isolation is one tab per worker plus the storage namespace, and nothing more. Two workers signed into the same site are the same session. The trace context (`setTraceContext`) is global, so records from concurrent workers interleave under whichever task id was set last. Chrome can stop the service worker at any time, which is why the run checkpoint, not memory, is the source of truth.

## Memory

- **Global: routes only** (`agent/memory/global/memory-store.ts`). After the planner confirms a task, the navigator's steps (host, path template, action and element role/type — never typed text) are saved under the start page's origin plus path template, with digit-bearing, long or user-worded segments generalized. Max 50 routes, 12 steps each, 30-day expiry, in `chrome.storage.local` (`wg_mem:routes`). A later task starting on the same page gets the route as an advisory note in its state message.
- **Per task:** findings from `save_findings`, the model's working memory string, and an in-memory archive of completed tasks in the conversation (`agent/memory/in-chat/task-archive.ts`). There is no fact, goal or constraint store.

## LLM layer

All calls go through `invokeLLM` / `invokeTools` in `agent/agents/base.ts`; models are built in `agent/helper.ts::createChatModel`; provider capabilities are in `packages/storage/lib/settings/llmCapabilities.ts` (`nativeTools`, `forceToolChoice`, `reasoning`, `audioInput`, `callTimeoutMs`).

- **Tools:** native tool calling (`bindTools`, forced tool choice where supported) with Zod validation and up to two re-asks carrying the issues; or the tools rendered into the prompt with a JSON reply for models without usable tool calling. A provider that rejects the tools payload switches that agent to the prompt fallback for the rest of the task.
- **Timeouts:** per provider and model from `callTimeoutMs` (e.g. 25 s Gemini/Vertex, 30 s OpenAI-compatible, longer for reasoning models, 90 s Ollama); a retry gets 1.5×.
- **Hedging:** a call still running after 10 s (`HEDGE_AFTER_MS`) is duplicated, unless that model was rate limited in the last minute (`NO_HEDGE_AFTER_RATE_LIMIT_MS`); the first reply wins and the other is aborted.
- **Transient errors** (timeout, 5xx, network) are retried once.
- **Rate limits and lost connections:** the server's hint (`retryDelay`, `retry-after`, capped at 30 s) or jittered exponential backoff, with a per-model cooldown shared by all callers. A call that gets no response at all ("Failed to fetch", `isNetworkError`) waits the same way. Once waiting would exceed 180 s in total (`RATE_LIMIT_BUDGET_MS`; a per-minute quota recovers in 20–60 s) the task is **paused** with a resumable checkpoint (`ChatModelRateLimitError`, or its subclass `ProviderUnreachableError` with the "back online" message).
- **Calls with a screenshot** get twice the time limit and hedge delay; screenshots are at most 1280 px wide, JPEG quality 60, with neutral element labels so a label's colour is never read as the page's.
- **Fatal errors** end the task: auth (401), bad request (400), forbidden (403), billing and exhausted quota (never treated as a rate limit), blocked URL, extension conflict, cancellation, max failures.

## Tracing

`trace.ts` records logs, events, every LLM call (latency, finish reason, token usage, tool calls, errors), re-asks and spans to IndexedDB (`WebGenieTraces`). Capture is always on in dev builds; in production enable Options → Developer → Enable Developer Options → Capture Traces. Download or clear traces there. The e2e harness saves them per task ([e2e.md](e2e.md)).

The separate LangSmith option (Developer → Langsmith Tracing) sends runs through the `langsmith` client from the executor and `helper.ts`.
